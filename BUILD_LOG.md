## 2026-07-28 (v0.10.0) — The 112-second freeze, a map sidebar you can reach, and the first tests the app layer ever had

**Michael found the one that mattered by using the thing.** He loaded an 11,000-row earthquake file, picked "Color by" on a density plot, hit the ID column by accident, and the app stopped. Not a crash — a **111.7-second** render (boxplot 105.3 s, scatter 28.7 s), and Shiny is single-threaded, so that is two minutes of a dead screen. Measured before touching anything: the cost is **linear in the level count** (30 levels 0.4 s, 100 → 1.1 s, 500 → 4.9 s, 1,000 → 9.6 s, 11,000 → 111.7 s), and suppressing the legend saved nothing, which killed the obvious "it's the legend" theory before it cost an afternoon. Root cause was an asymmetry nobody had noticed: the **facet** picker has been capped at 30 levels since it shipped (`cols_cat`), the **colour** picker was fed `cols_all()` with no cap at all, and `build_full_plot`'s sanitiser only dropped a *numeric* high-cardinality group — a character/factor ID sailed straight through. `GROUP_MAX <- 50`, dropped in the BUILDER not the renderer, because `current_outputs()` feeds mod_export and mod_report too and its `tryCatch` catches errors, not hangs: a renderer-only gate would have left the download paths frozen. 111.7 s → **0.30 s**. Lesson: when one picker gets a cardinality cap, check every sibling picker feeding the same builder.

**The cap and the message explaining the cap disagreed about NA.** `chart_hint` counted with `n_distinct(..., na.rm = TRUE)`; `build_full_plot` and `generate_code` used the default. One rule, three copies, two counting conventions — so a column with exactly 50 real categories plus one blank was silently stripped of its colouring with **no explanation at all**, which is precisely the failure the hint exists to prevent. Settled which side was right by *execution* rather than argument: running ggplot showed NA gets its own level and its own legend key (3 levels + NA = 4 distinct colours), so NA genuinely costs a slot and the builder was correct. Aligned the hint to it.

**Two bugs were the code generator drifting from the builder — the house rule's exact failure mode.** P5 made `p$geojson` alone the choropleth mode flag so a half-configured shaded map returns NULL instead of quietly drawing a points map; `generate_map_code` kept the old two-condition gate and fell through, so the pane correctly said "pick the region property…" while the R-code tab showed a **complete points script** that drew an unrelated scatter. Three separate review lenses found it independently. Builder and code generator are a matched pair; changing mode detection in one is always a two-file edit.

**The heatmap and "combine points by area" were mutually exclusive for no good reason.** Two independent suppressions (a conditionalPanel removing the checkbox, and `admin_cluster_params` forcing `heatmap = FALSE`), both there because `build_leaflet_map` aggregates `d` in place, so a heat layer built afterwards would have described a dozen centroids. The fix was one line **earlier**: `d_pts <- d` before the aggregation, and the two compose — density underneath, per-area counts on top. Before disabling a feature because a transform destroys its input, check whether the input can just be stashed.

**The app layer had never been tested — and proving the new tests worked changed the result twice.** Twelve `mod_*` servers and eight `run_*` launchers had **zero** automated coverage against 4,279 lines of helper tests: exactly inverted from where bugs actually escaped. Added `test-modules.R` and `test-launchers.R`, then **mutation-tested them rather than trusting them**. Reverting `GROUP_MAX` → 10 failures, caught. Re-forcing `heatmap = FALSE` → 8 failures, caught. Stripping the new property-picker labels → **0 failures, escaped** (the helper was tested; nothing asserted the module *used* it). Mutating `mapServer("map")` to `("mapp")` → **0 failures, escaped** — a module server with an id that has no matching UI runs happily in its own empty namespace, its outputs never bind, and the tab renders blank with no error, so no *runtime* test can observe it. That one needed a structural check: deparse each app builder and require every `<mod>Server("id")` to appear in some `<mod>UI("id")`. A test that cannot fail is worthless; mutation is the cheapest way to find out which ones those are.

**The docs audit caught a code bug the code review missed.** Auditing every document against the source (26 corrections taken, 13 rejected as wording preference) turned up that the new colour-cap hint told users to "use it as a facet" — but the facet picker only offers columns with ≤30 levels, so any column tripping the 50-level cap is never offered as a facet either. Advice the user cannot act on is worse than none. Also flatly wrong in README: "the only mini-app with a Report tab", two screens after the same file said all eight have one. **Audit docs against the CODE, never against another doc** — and the pass that rejects bad corrections is worth as much as the one that finds them, since rejecting the `influence.ME` proposal is what surfaced a real CLAUDE.md error (a "graceful requireNamespace fallback" that does not exist).

**Review numbers:** 6 finder lenses → 25 candidates → 3 refuters each → **8 survived, deduping to 3 real defects**. The refuters killed 17, including a Date-colour bug that reproduced identically on the previous release — pre-existing, not introduced, correctly left alone. Suite **1,372 → 1,607 → 1,619** after the review fixes, 0 failures; `R CMD check --as-cran` 3 NOTEs, all environmental. Published as `8cf7d6e`, tag v0.10.0.

## 2026-07-27 (v0.9.0) — Boundaries in the box, a report in every app, and a 580× freeze fix

**Shipping bigger data detonated a latent quadratic.** `geojson_bounds()` walked GeoJSON coordinates appending one position at a time (`lng <<- c(lng, ...)`). Fine on the hand-made test fixtures; on the new **3,222-feature** US counties set it took **~13 s per call** and re-ran on every settings change, so picking "US counties" froze the app for ~20 s at a time, repeatedly. Flattening each feature once with `unlist(use.names = FALSE)` and reading interleaved lng/lat off `seq.int()` gives byte-identical bounds **580× faster** (11.6 s → 0.02 s; a full national choropleth 21.8 s → 0.46 s). `<<- c()` inside a walker is a performance bomb that only detonates when the data gets big — and the release that ships bigger data is exactly when it goes off.

**The report and the screen disagreed, and the report was wrong.** `lmer_report_payload` called `names()` on `lmer_fit_stats()`'s **Statistic/Value data frame** as though it were a named list, so ten fit statistics collapsed into two mislabelled rows ("Statistic | AIC"). The module's own tab was right; only the download was wrong, which is the worst kind of disagreement. A second one in the same area: dropping `VarCorr()`'s `var2` column flattened the intercept–slope **correlation** row into the variance list, so a random-slope model reported a **negative variance and SD**. Dropping a column that distinguishes row *types* turns a valid table into a plausible-looking wrong one.

**Three silent-FALSE / silent-drop bugs worth naming.** `isTRUE(p$geo_builtin)` was always FALSE because `geo_builtin` is a *string* key, not a logical — so the built-in-vs-upload diagnostic never fired. `MAP_CHORO_MAX = 3000` would have clipped **222 counties** off a national map without saying so (raised to 4000, and truncation now reports itself). And unticking a report section still *paid* for it: `avail()` read every optional reactive regardless of the picker, and reading a map's reactive rebuilds its widget — an opt-out that still evaluates the thing you opted out of isn't an opt-out.

**Shipped data needs a re-runnable builder or the provenance claim is unverifiable.** `dev/build_boundaries.R` — the sole record of where the boundary files came from — had a hardcoded scratchpad path, a hardcoded Desktop output, and assumed a download already existed locally. Made it refuse to run outside the package root, scratch in `tempdir()`, and write to `inst/geo`. It was also **non-reproducible**: `st_write` derives the GeoJSON layer `"name"` from the output file stem, so writing to `tempfile()` baked a random string (`"name": "file173995825dd02"`) into the shipped data and every rebuild differed. Any tool that reads metadata off a *file name* makes `tempfile()` a reproducibility hazard.

**Driving the app caught what 53 agents missed.** The review confirmed that re-rendering the choropleth sidebar without `selected=` wiped the user's picks when the boundary filter changed — but clicking through the fixed build showed the join still falling to **"0 of 67 regions matched"**, because `region_prop` was not merely unset but *actively re-imposed* with the built-in's default key over a deliberate choice. A full-sidebar `renderUI` is a state-destroying operation, and adding a new re-render trigger silently weaponizes every input inside it that lacks an isolate-and-restore. **Review and drive; they catch different things.**

**Review numbers:** 53 agents, 5 lenses × 3 refuters, **11 confirmed / 4 refuted as already-fixed**, plus the region_prop fix found by hand. Suite 1,349 → 1,365 → **1,372**, 0 failures; `--as-cran` 3 environmental NOTEs. Published as `2d7156f`, tag v0.9.0.

## 2026-07-23 (v0.8.0) — The field-testing punch list: nine commits in seventy minutes, and a placeholder that trapped you in a dropdown

**The best bug of the round was three characters wide.** Once you picked a "Split by" variable in Compare Groups you could never get back to unsplit: "(none)" was right there in the choices and simply would not click. It carried the **empty-string value** — `c("(none)" = "", groupable_cols(df))` — and selectize reserves the empty string as its *placeholder*, so it is never rendered as a selectable row. Server logic was fine the whole time. Never give a real, selectable choice the empty-string value; use an explicit sentinel (the house `__none__`) and map it to NULL server-side.

**"Cluster by county" could not be built with the clustering plugin at all.** leaflet.markercluster clusters by **screen proximity** and has no notion of a data column, so the feature had to become **pre-aggregation**: one bubble per admin value at the centroid of its points, sized by count. When the widget's built-in feature is the wrong abstraction, aggregate before handing it over — and route the builder *and* the code generator through one shared params-rewrite (`admin_cluster_params`) so they cannot drift. Two bugs fell out of the aggregation itself: an area whose points straddle the **antimeridian** (+179 / −179) landed at longitude 0, the opposite side of the planet, because a plain arithmetic mean of longitudes is not a valid circular mean; and a user column literally named `Points` was silently overwritten by the per-area count alias, so the alias now checks for a collision and falls back to the dot-prefixed internal name.

**Two "compute then throw away" mistakes.** An over-the-cap stratified compare grid computed up to **144 analyses** and then discarded all of them, because the only cap check was a post-gate on the result. When a limit is deterministic from the user's picks, gate *before* the expensive call and keep the post-gate as a backstop. Separately, `compare_grid` did `as.character(svr)` before testing missingness — and `as.character(NaN)` is the ordinary-looking string `"NaN"`, which matches no level and is not NA, so the sidebar preview and the actual grid disagreed about how many rows fell in no stratum. Test missingness on the RAW vector.

**`fillable` is a property of the content, not the app.** The Regression Estimated-means controls rendered as a clipped inner scroller in the Data Explorer but were fine in the standalone Regression Tool — the explorer listed `"regression"` in `page_navbar`'s fillable set, and the EMMeans tab leads with a flexible controls card, which a fillable host squeezes to the viewport. Tabs that are long scrolling stacks must not be fillable, and cards that must keep their natural height should set `fill = FALSE` so they are host-independent.

**Word reports chunked wide tables at the wrong seam.** `.docx_add_table` used `split_wide_df`'s default `keep = 1L`, but this kit's wide frames are **multi-keyed** — grouped summaries by group(s) + Variable, the stratified compare grid by Outcome + Group + Stratum — so the second chunk's rows could not be identified. "Repeat the label column" is not a general rule; detect the leading run of non-numeric columns instead. And a small one worth remembering: putting `REPORT_WIDE_COLS <- 8L` between `df_to_html`'s roxygen block and the function **silently detached the docs** — roxygen binds to the immediately following object.

**Numbers:** nine commits B0–B8 between 13:18 and 14:27, suite **1,240** passing / 0 failing across 15 files at B8; the release review confirmed **14** findings. Published as `cd4b828`, tag v0.8.0.

## 2026-07-23 (v0.7.0) — A colleague's app absorbed, and the release that killed the orphan force-push

**The eighth app arrived as somebody else's single file, and the absorption *was* the job.** Laina Edwards (GitHub `Lainanoel`) contributed a standalone "Quick GLMM Review" app; 0.7.0 is the record of taking it apart along the house seam — 539 lines of pure engine (`helpers_glmm.R`), a thin 649-line module, a 91-line launcher. What was deliberately **not** rewritten is the interesting half: `bq()`, `build_random_part()`, `emm_spec_formula()`, `is_categorical()`, `round_df()`, `make_combined_factor()`, `MAX_FIXED` and `snapshot_rng()` were all reused from the lmer kit rather than re-implemented, so only the genuinely GLMM-specific parts stayed — the family registry, the domain check, the ziformula/dispformula side-model builder, the glmmTMB wrapper, DHARMa, and the code generators. One namespace forced one rename: `make_example_data()` already belonged to the lmer kit, so the GLMM generator shipped as `make_glmm_example_data()` — and it carries the v0.5.0 RNG lesson forward, snapshotting `.Random.seed` before its `set.seed(2024)`.

**One module, instantiated twice, on purpose.** `glmmUI(id, binary = FALSE)` is the General tab; `binary = TRUE` is the 0/1 tab with a link picker and no dispersion model — because 0/1 data has **no free dispersion parameter**, and a shared path would have to silently ignore half its own controls. The module says so in its own comment: keeping the binary path separate avoids the "it silently did something odd with my 0/1 column" failure mode. It also *says on screen* which level it models (`Modeling P(present = "1")`) rather than leaving the user to guess the direction.

**Absorbing someone else's code found a real statistical error in it.** The original ran Type III Wald ANOVA on treatment contrasts. Type III is only interpretable under **sum-to-zero contrasts**; without them the main-effect tests answer a different question. Fixing it moved a p-value from **0.006236 to 0.000512**, and another term from 0.521094 to 0.161496 — while the *interaction* row stayed invariant to three significant figures, which is exactly the diagnostic tell that the contrasts were the problem. Worth remembering as the argument for absorption over adoption: porting to the house pattern means reading every line.

**A pure helper opened a graphics device.** `glmm_dharma_tests()` called DHARMa's test battery with plotting left on, which wrote a stray `Rplots.pdf` and tripped an existing test that asserts no device is left open. `plot = FALSE`. A helper must not open a device — that is what makes it testable in the first place.

**Michael's screenshot fixed the diagnostics panel.** The default DHARMa plot rendered boxplot axis labels like `0.0943396226415094`. Replaced with `glmm_dharma_plot()`: signif-3 predicted-response labels, an annotation-free QQ, and the uniformity test printed separately as text. Nothing in the test suite could have caught this; someone had to *look at it*.

**The release mechanics were the point.** Laina had to appear as a contributor on the public repo, which meant the old ritual — a single orphan commit force-pushed over `main` — had to die. She forked, committed under an email verified on her GitHub account (`53e9ac2`, 1,915 insertions across 12 files), and opened PR #1; the merge (`26da427`) and the docs commit (`99bbda2`) sit on top. From here the public repo keeps **permanent multi-commit history** and is never force-pushed again, because contributor credit is now part of the record.

**Review numbers:** 27 agents, 6 lenses, 3 refuters per finding, **7 confirmed / 0 refuted**. Suite 1,094 → 1,103 → **1,121**; `R CMD check` Status: OK. Published as `99bbda2`, tag v0.7.0.

## 2026-07-21/22 (v0.6.0) — New Mac, deep Regression, map-in-report, choropleth + heatmap, split-by, a seventh app

**Dev machine moved Windows → macOS/arm64** (R 4.5.1). Every CLAUDE.md "PowerShell only" gotcha is dead here — plain `Rscript` in any shell, no segfault, and `shiny::testServer` WORKS (it segfaulted on the Windows box; module-level tests are now possible). One trap came with the move: **`capabilities("cairo")` reports TRUE but lies** — grDevices' cairo.so links XQuartz libs that aren't installed, so `cairo_pdf()`/`svg()` open no device, write nothing, and raise only a warning. **Onboarding audit first** (102-agent workflow: 9 area maps + 3 probes, 88 raw findings → 47 adversarially confirmed). ## 2026-07-16 (v0.5.0) — Map layer groups + color scales, self-contained HTML, and THE set.seed/chromote bug

Michael's worklist round. Features: **"Group layers by" a column** (≤ `MAP_GROUP_MAX` 12 levels → one toggleable overlay per level via `addLayersControl(collapsed = FALSE)`, clustering per group so clusters never mix regions, "Focus on group" flyTo, auto-color-by-group when no color picked — chosen over choropleth for v0.5 because it works with ANY data, zero boundary shipping; choropleth stays roadmap #1) and **log / quantile color scales** for continuous colors (`map_color_scale()` is the single fallback rule — log needs positives, quantile needs unique breaks — consulted by builder, code-gen AND map_hint so all three agree; log legend back-transforms via `labelFormat(transform = 10^x)`). Grouped maps changed the code-gen shape: a readable `for (g in groups)` loop instead of one pipe, with popup/radius as `df$popup_text`/`df$radius_px` columns so the loop subsets cleanly. Import filter "Values" picker now populates via `updateSelectizeInput(server = TRUE)` — the client-side list silently capped rendered options on high-cardinality columns.

**Export rewrite.** The pandoc/zip fallback (users double-click the html INSIDE the zip → no `map_files/` → blank page) is gone: `inline_html_deps()` post-processes `saveWidget(selfcontained = FALSE)` output into ONE file — scripts become `data:application/javascript;base64` src (sidesteps `</script` escaping entirely), stylesheets inline as `<style>` with their `url(...)` icons data-URI'd, and replacement is spliced via `strsplit(fixed)+paste` because gsub would interpret backslashes in JS payloads. Verified the hard way: the file is moved AWAY from its support folder and screenshotted headless — 198 KB of rendered markers (a blank page is ~10 KB). Dropped `zip` from Suggests.

**The PNG bug was a beauty — root cause: `set.seed()` in example data.** Michael's in-app error ("Cannot find an available port… Failed to start chrome… Chrome is available on your system") reproduced only in app-like processes, never in bare probes. Bisected: `load_all` fine, `make_map_example_data()` → 100% fail. The fixed seed left the session RNG at a state where **chromote's `with_random_port()` drew the same blocked port (3824) every single time**. Confirmed deterministically: same "random" ports printed run after run, same failure; unseeded processes always fine. Fix: `snapshot_rng()` (helpers_stats.R) — every fixed-seed site (`make_map_example_data`, `make_example_data`, `do_subset`) now restores `.Random.seed` via `on.exit`, closing the review sweep's deferred RNG finding too, with regression tests asserting the stream is untouched. Also: current Edge builds refuse the OLD headless mode ("debugging port not open") → `.chromote_env()` prefers `CHROMOTE_HEADLESS=new` proactively, and `save_map_png` retries once with a fresh browser (`.reset_chromote()`) before reporting `chromote_info()` diagnostics. **Lesson for the log: never bare-`set.seed()` in package code — it makes *other packages'* randomness deterministic, and one of them picks TCP ports.**

Suite 656 green; grouped+log widget/codegen smoke incl. standalone eval; both apps boot; R CMD check Status: OK.

## 2026-07-16 — Map Tool: leaflet point maps + a sixth app (v0.4.0), plus three bug fixes

New feature area: ArcGIS-style interactive point maps. Same shape as every other feature — pure `helpers_map.R` → thin `mod_map.R` → `run_map_tool()` launcher + a **Map tab** in the Data Explorer (between Visualize and Compare Groups). **New Imports: `leaflet` (2.2.3, MIT, Posit-maintained), `htmlwidgets`, `htmltools`** (the latter two were already transitive via shiny); **new Suggests: `webshot2`, `chromote`, `zip`** — PNG snapshots and the no-pandoc HTML fallback degrade gracefully. Scope decisions (Michael): points-from-lat/lon only in v1 (no choropleth/sf — a points app needs zero GIS system deps), mini-app + Explorer tab, HTML + PNG export, general-purpose examples.

**Design was produced by a two-perspective plan + adversarial merge** (architecture-first vs map-UX-first, then a critic verifying both against the source). **The "bug" that wasn't.** Steel flagged B-A significant where Dunn didn't, which looked backwards ("Steel is more conservative"). **`posthoc_name` replaces `grepl("Kruskal", test)`.** The post-hoc label was inferred by pattern-matching the test name in **five** places (mod_compare x3, helpers_report x2) + `compare_code`. That inference becomes *wrong* the moment Kruskal can carry either Dunn's or Steel-Dwass, so results now carry an explicit `posthoc_name`. (Kept the `grepl` that picks the *statistic symbol* — that one is legitimately about the test.) Deleted the dead `group_stats_table()` (zero callers since `oneway_means` superseded it).

**Fifth app.** `run_compare_groups()` / `compare_groups_app()`, About -> Import -> Compare -> Export -> Report.
